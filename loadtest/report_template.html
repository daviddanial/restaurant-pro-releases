Load test · concurrent radiologist reading

TeleRad Reading Load Test

Can TeleRad serve 10+ radiologists opening and reading large studies at the same time? The server can. The viewer's loading pattern is what makes a full CT slow.

Local test environment · 14–15 Oct 2026 · 60 synthetic studies · 2 full runs of 28 scenarios + 5 control runs

Yes, TeleRad handles 10 and 20 concurrent CT readers. There were zero errors in every run, the first CT or MR image appeared within 2.5 s at 10 readers, and the server averaged at most about 1.5 CPU cores at 50 Mbps per reader. With the browsers off the machine, full-study time at 20 readers was the same as at 1 reader.

The miss is the full CT study at 50 Mbps: 76 s uncompressed and 50 s JPEG-LS, against a 60 s target. That time comes from the viewer fetching one image at a time with no prefetch, and from sending uncompressed pixel data. It is not a capacity limit.

Targets

Met
Time to first image < 3 s at 10 concurrent readers (CT, MR)
CT at 10 readers on 50 Mbps: 0.43 s worst simulated reader, 1.97 s worst real browser. MR: 0.39 s / 1.93 s. The worst browser in any CT or MR scenario was 4.8 s, at 20 readers unthrottled, when the test machine's CPU was saturated by the browsers.
Missed
Time to first image < 3 s for uncompressed CR/DX
Each uncompressed CR image is 15 MB, which takes 2.4 s to transfer at 50 Mbps. At 10 readers: 3.3 s simulated, 3.5 s browser. The same image stored as JPEG-LS (5.5 MB) showed in 1.5–2.6 s.
Partly

JPEG-LS CT (113 MB): 50 s with simulated readers only, 57 s with browsers on the same machine. Uncompressed CT (273 MB): 76 s, and 87 s with browsers. Real browsers, which also decode every image, took 93–110 s. One reader alone already takes 75 s for uncompressed CT, so this is not caused by concurrency.

Bottlenecks, with evidence

1. The viewer fetches one image at a time, only when it is shown

In a captured viewer session each scroll step issued exactly one full-DICOM request, with nothing fetched ahead. So every image pays a full round trip: at 50 ms latency, 520 images add 26 s to a CT. For one reader, study size ÷ bandwidth + 520 × 50 ms predicts 69.7 s, and 74.5 s was measured. Scrolling can't go faster than about 7 images/s at 50 Mbps (step 140–155 ms) or 3.6 images/s at 20 Mbps (270 ms).

2. Uncompressed pixel data is 2.4× larger than it needs to be

The same CT is 273 MB uncompressed and 113 MB as lossless JPEG-LS: 76 s vs 50 s at 50 Mbps. For CR/DX the gap decides the first-image target: 15 MB per image (3.3 s) vs 5.5 MB (1.5 s).

3. Not the server: it has large headroom

With simulated readers only, full-study time at 50 Mbps was 79.5 s at 1 reader, 76.5 s at 10 and 75.7 s at 20 (uncompressed). There was no degradation. At 20 readers the API averaged 0.6 core and MinIO 0.3, memory was flat, and iowait was about 0. Unthrottled, 20 readers pulled 200 MB/s (1.6 Gbps) on about 5 server cores. At that rate this machine's server share should cover roughly 30–40 readers at full 50 Mbps. That figure is an extrapolation, not measured.

4. Client-side decode and render are a real cost

Headless browsers used about 6 of 8 cores (software WebGL). That made simulated readers 10–15 s slower in the browser runs than in the controls. Unthrottled, real browsers took longer on JPEG-LS CT (54–58 s) than on uncompressed (43 s), which is the decode cost. Workstations with their own CPU and GPU will do better, but prefetch is what hides decode time.

5. "Warm" is no faster than "cold"

Image responses have no Cache-Control or ETag, so re-opening a study re-downloads all of it. On the server, MinIO read from disk on every request (disk reads tracked bytes served in every run), so cold and warm runs matched (CT 10 readers at 50 Mbps: 86.4 vs 86.5 s).

Recommendations, in priority order

  1. Prefetch the image stack in the viewer

    Keep 6–10 requests in flight, starting from the current slice and working outward. Expected impact: removes the 26 s of per-image waiting. At 50 Mbps a full CT should take about 44 s uncompressed and 18 s JPEG-LS (estimate), which meets the target. Scrolling becomes instant once images are cached, and decode overlaps transfer. Client-only change; the measured server headroom covers the burstier load.

  2. Store or serve pixel data compressed

    Keep compressed studies as received and transcode uncompressed ones to lossless JPEG-LS or HTJ2K at ingest. Expected impact: 2.4–2.7× fewer bytes (CT 273 → 113 MB, MR 168 → 70 MB, CR 15 → 5.5 MB per image). Uncompressed CR/DX first image at 50 Mbps drops from about 3.3 s to about 1.5 s. Costs ingest CPU and client decode time.

  3. Add caching headers to image responses

    Instances never change for a given SOP UID, so Cache-Control: private, max-age=…, immutable plus an ETag is safe. Keep the cache private and scoped to the session policy for shared workstations. Expected impact: re-opening a study, or loading it again as a comparison prior, comes from the browser cache instead of a full re-download (273 MB per CT today).

  4. Show a preview first for large single images (CR/DX/MG)

    The server already has a rendered-JPEG frame endpoint. Show that first, then swap in full fidelity. Expected impact: first image under 1 s regardless of a 15–50 MB original.

  5. Stream images instead of buffering them in memory

    The API reads each whole object into memory before sending it. That isn't a problem today (memory flat at about 1.1 GB), but memory per request equals object size. Expected impact: safe headroom for multi-frame US/XA and tomosynthesis (hundreds of MB per object) at 20+ readers, and an earlier first byte on large files.

  6. Re-test on production-like hardware before claiming a ceiling

    Use a separate load-generation machine, the production frontend build, the real reverse proxy (HTTP/2) and multi-frame data. Expected impact: confirms or corrects the 30–40-reader estimate. Adding API instances is not needed at 20 readers based on these numbers.

Other findings

  • Ingest errors. Upload batches for the same study processed concurrently raise duplicate-key exceptions in the ingest worker: 440 stack traces while loading the test data. Final instance counts were correct, so the messages are retried, but the log noise hides real errors.
  • Wrong transfer syntax stored. Every instance is recorded with transfer syntax Explicit VR Little Endian, including JPEG-LS files (IngestWorker.java:137 reads the tag from the dataset, not the file meta).
  • Duplicate open requests. The dev-mode viewer requests /api/studies/{id} twice and /priors three times per study open.
  • RabbitMQ idle CPU. RabbitMQ idles at about 0.45 core.

Method and limits

  • Test data: synthetic phantoms, no patient data. 20 CT (520 × 512², 273 / 113 MB), 20 MR (320 × 512², 168 / 70 MB), 20 CR (2 × 3000×2500, 30 / 11 MB). Half of each is JPEG-LS lossless, ingested through the hospital upload API. Every reader opens its own study under its own account.
  • Simulated readers replay the captured viewer requests: study, priors, then one full-DICOM GET per image in order, with a 30 s timeout.
  • Network shaping uses a per-reader token-bucket proxy (no root for tc), checked to within 5% of theory. It shapes API traffic only; app code was served unshaped.
  • One 8-core machine ran servers, load generator and browsers, so browser results are pessimistic. The control runs show server-only behavior.
  • Not tested: production build and reverse proxy, separate client hardware, GPU rendering, multi-frame cine, HTJ2K, more than 20 readers, dropping the OS page cache (needs root, though MinIO read from disk anyway).
